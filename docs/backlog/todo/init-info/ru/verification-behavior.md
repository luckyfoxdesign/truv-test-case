# Truv — Dashboard: исходная логика и поведение

Документ фиксирует поведение исходного интерфейса (**Control A**) на основании предоставленных скриншотов и описаний пользователя. Гипотезы редизайна сюда не включены.

## 1. Переход на Dashboard

- Пользователь открывает страницу проверки работодателя, например [Employment Verification for Walmart](https://truv.com/verifications/walmart-employment-verification).
- На лендинге нажимает **Verify Walmart employee**.
- Открывается страница **Dashboard**.

## 2. Структура Dashboard

В основной колонке разделы расположены сверху вниз:

1. **Borrower details** — данные заёмщика; содержит обязательные поля.
2. **Verification details** — тип проверки, работодатель и кнопка **Add employer**.
3. **Your information** — данные инициатора проверки; содержит обязательные поля.
4. **Continue** — кнопка перехода к оплате.

В правой колонке отображается **Order summary** — состав и стоимость заказа. На предоставленном примере первоначальная цена составляла **$50**.

Разделы **Borrower details** и **Your information** находятся на одной странице. Обязательной последовательности ввода отдельных полей пользователь не описывал; порядок расположения разделов не следует путать с последовательностью завершения событий аналитики.

## 3. Добавление работодателя

1. Нажатие **Add employer** добавляет ещё одно поле ввода работодателя.
2. Когда пользователь вводит в это поле значение, соответствующий работодатель появляется в **Order summary**, а общая сумма заказа пересчитывается.
3. Пока добавленное поле остаётся пустым, новый работодатель в **Order summary** не появляется и сумма не меняется.

**Важно:** добавление пустого поля само по себе не меняет состав и стоимость заказа.

## 4. Order summary

- Показывает выбранный тип проверки, работодателей и стоимость заказа.
- Динамически обновляется после ввода дополнительного работодателя.
- Не добавляет в сводку пустое поле работодателя.
- На исследованном экране стартовая цена заказа — **$50**.

## 5. Кнопка Continue

- Находится внизу страницы после разделов формы.
- **Неактивна**, пока не заполнены все обязательные поля обеих основных секций.
- Становится активной после заполнения обязательных полей.
- По нажатию открывает модальное окно оплаты **Payment information**.

Заполнения только **Borrower details** недостаточно: обязательные поля **Your information** тоже должны быть заполнены.

## 6. Видимость и прокрутка

При доступной высоте окна браузера **840 px**:

- Раздел **Your information** не виден без прокрутки вниз.
- Кнопка **Continue** также находится ниже первого экрана.
- В исходном интерфейсе нет явного индикатора прогресса заполнения.

Это наблюдение для указанной высоты экрана; поведение на других размерах экрана не проверялось.

## 7. Форма оплаты

После нажатия активной кнопки **Continue**:

- Открывается модальное окно **Payment information** поверх Dashboard.
- Доступны варианты **Apple Pay**, **Google Pay** и оплата банковской картой.
- Для карты отображаются поля номера, срока действия, кода безопасности и страны.
- Показаны условия оплаты и ссылки на соглашения.
- Основное действие — **Start a verification**.
- Модальное окно можно закрыть и вернуться на Dashboard.
- В окне указано, что Truv взимает плату только за **успешные проверки**.

## 8. Последовательность интерфейса

```text
Landing Page
    ↓ Verify
Dashboard Loaded
    ├─ Borrower details
    ├─ Verification details (Add employer → Order summary)
    ├─ Your information
    └─ Continue (после заполнения обязательных полей)
         ↓
Payment information (модальное окно)
         ↓
Start a verification
```

Схема отражает расположение разделов и доступные действия, **а не подтверждённую последовательность аналитических событий**. Завершение оплаты и последующий результат проверки требуют отдельного подтверждения.

## 9. Что не установлено

- По какому действию фиксируются события `Borrower Information Completed` и `Your Information Completed`.
- Можно ли продолжать с пустым добавленным полем работодателя.
- Сохраняются ли введённые данные после перезагрузки страницы.
- Как выглядит результат нажатия **Start a verification** при успешной и неуспешной попытке.
- В какой момент фиксируется событие `Verification Payment Completed`.

Этот документ описывает **исходный Dashboard (Control A)** для дальнейших UX-экспериментов.
