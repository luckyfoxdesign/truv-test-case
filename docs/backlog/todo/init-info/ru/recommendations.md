## 1. Prioritization

На основе масштаба оттока, финансовых сценариев и наблюдаемых UX-рисков предлагается следующая предварительная приоритизация.

| Priority | Area                 | Rationale                                                                                                                                           |
| -------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0       | Analytics Validation | Без корректных событий невозможно достоверно установить причины потерь и измерить результаты улучшений                                              |
| P1       | Dashboard Completion | Крупнейший отток внутри продукта и наибольший расчётный эффект от улучшения конверсии. Изменение тут, повлечет изменения на всех последующих этапах |
| P2       | Payment Completion   | Существенный отток непосредственно перед финальным событием                                                                                         |
| P3       | Landing Page         | Крупнейшие абсолютные потери, но неизвестно намерение посетителей                                                                                   |
| P4       | Verify → Dashboard   | Конверсия 99.17%; ограниченный потенциал улучшения                                                                                                  |

Приоритеты относятся к **исследованию и проверке гипотез**, а не к подтверждённым дефектам интерфейса.

## 2. Recommended Action Plan

### 2.1. – Validate Analytics

#### Цель

Убедиться, что показатели действительно соответствуют действиям пользователей.

Проверить определения событий:

- Your Information Completed;
- Borrower Information Completed;
- Verification Payment Completed;

и порядок регистрации и настройки последовательной воронки.

Затем дополнить аналитику:

| Metric                             | Purpose                                                                                                                                 |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Form Start Rate                    | Доля пользователей, начавших заполнять форму                                                                                            |
| Form Progress                      | Доля заполненных обязательных полей                                                                                                     |
| Section Completion                 | Завершение каждого раздела независимо от порядка                                                                                        |
| Validation Errors                  | Частота и типы ошибок заполнения                                                                                                        |
| Abandonment by Progress            | На каком этапе пользователь прекращает заполнение                                                                                       |
| Continue Click Rate                | Доля пользователей, нажавших Continue                                                                                                   |
| Payment Modal Open Rate            | Доля пользователей, открывших платёжную форму                                                                                           |
| Payment Modal Abandonment Rate     | Доля пользователей, закрывших платёжную форму без попытки оплаты                                                                        |
| Payment Attempt Rate               | Доля уникальных пользователей, совершивших хотя бы одну платёжную попытку                                                               |
| Payment Attempt Count              | Общее количество платёжных попыток, включая повторные                                                                                   |
| Unique Payment Users               | Количество уникальных пользователей, совершивших платёжную попытку                                                                      |
| Payment Attempts per User          | Среднее количество платёжных попыток на одного пользователя, пытавшегося оплатить                                                       |
| Payment Success Rate (per Attempt) | Доля успешных попыток от общего количества платёжных попыток                                                                            |
| Payment Failure Rate (per Attempt) | Доля неуспешных попыток от общего количества платёжных попыток                                                                          |
| Unique Payment Conversion Rate     | Доля уникальных пользователей, успешно оплативших хотя бы один раз                                                                      |
| Payment Decline Reason             | Причины отказа банка или провайдера: недостаточно средств, подозрение на мошенничество, заблокированная или заявленная украденной карта |
| Payment Authentication Failure     | Ошибки, отказы или отмены 3D Secure / SCA                                                                                               |
| Payment Processing Error           | Технические ошибки платёжного шлюза, тайм-ауты, недоступность провайдера                                                                |
| Payment Retry Rate                 | Доля пользователей, повторивших платёжную попытку после неудачи                                                                         |
| Payment Recovery Rate              | Доля пользователей, успешно оплативших после первоначальной неудачи                                                                     |


### 2.2. – Investigate Dashboard

#### Цель

Найти реальные причины незавершённого заполнения.

#### Проверить

- Видят ли пользователи все разделы;
- Понимают ли объём обязательных данных;
- Какие поля вызывают затруднения;
- На каком проценте заполнения прекращают взаимодействие;
- Понимают ли условия активации Continue;

#### Возможные UX-гипотезы для тестирования:

- Разделение формы на шаги;
- Индикатор прогресса;
- Улучшение видимости следующего действия;
- Более понятная обратная связь при валидации;

### 2.3. – Investigate Payment

#### Цель

1. Отделить отказы от оплаты от ошибок платёжного процесса.

#### Необходимо измерить переходы

1. Continue Clicked →
2. Payment Modal Opened →
3. Payment Attempted →
4. Payment Completed.

#### Дополнительно проверить

- Причины закрытия модального окна;
- Ошибки платёжных полей;
- Влияние стоимости заказа;

### 2.4. – Investigate Landing Page

#### Цели

1. Определить, какая часть посетителей действительно намерена заказать проверку.
2. Проанализировать источники трафика, поисковые запросы и различия между категориями пользователей.

На основании результатов проверить гипотезы о понятности услуги, стоимости и следующих шагов.

### 2.5. – Validate Improvements

После подтверждения причин оттока провести UX-тестирование и контролируемые эксперименты.

#### Основная продуктовая метрика

1. Конверсия Dashboard →
2. Verification Payment Completed.

#### Дополнительные метрики

- Form Completion Rate;
- Payment Completion Rate;
- Средняя стоимость заказа;
- Доля успешно оплачиваемых проверок;

## 3. Limitations of This Assessment

Исследование основано на предоставленной воронке, изучении интерфейса и наблюдениях за его поведением.

В рамках тестового задания сделаны следующие допущения:

1. Все показатели относятся к одному сопоставимому периоду и указанной пользовательской выборке.
2. Данные воронки отражают уникальных пользователей в последовательной модели.
3. Для финансового моделирования используются условные цены $35 и $50, а не фактический средний чек.
4. Последующие коэффициенты конверсии при моделировании улучшения остаются постоянными.
5. Дополнительные финальные события условно считаются оплачиваемыми заказами.
6. Финансовые результаты не экстраполируются на месяц или год, поскольку период наблюдения неизвестен.

Реальные потери выручки, доходность и эффект UX-изменений невозможно достоверно рассчитать без дополнительных продуктовых и финансовых данных.

## 10. Final Recommendation

**Главная возможность роста находится между открытием Dashboard и завершением оплаты.**

Текущая воронка показывает значительные потери пользователей, однако недостаточная детализация и возможные проблемы последовательности событий не позволяют установить причины отказов.

Финансовые сценарии указывают на высокий потенциальный эффект от улучшений *Dashboard* и процесса оплаты.

#### Рекомендуемая последовательность

1. Проверить корректность аналитики;
2. Определить реальные причины оттока;
3. Приоритизировать подтверждённые UX-проблемы по влиянию на бизнес;
4. Протестировать изменения и измерить влияние на конверсию и оплачиваемые проверки;

Такой подход позволяет перейти от предположений к измеримым продуктовым решениям и обоснованно направлять ресурсы на развитие продукта.
